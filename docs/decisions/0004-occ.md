# ADR-0004: Optimistic Concurrency Control for Branch Head

- Status: Baseline
- Date: 2026-09-06

## Context

In multi-user collaboration or multi-agent execution environments, multiple callers may read the same Branch head and attempt to append new Nodes simultaneously.

Without concurrency control, one caller could overwrite the branch pointer updated by another caller (lost updates).

Heavyweight distributed locking across conversation branches would introduce performance bottlenecks, deadlocks, and complexity.

## Decision

Branch head advancement MUST employ Optimistic Concurrency Control (OCC) using a monotonically increasing `version` field.

The Branch model carries a `version: u64`.

Advancing the branch pointer requires a Compare-And-Swap (CAS) semantic:
`UPDATE branch SET head = :new_node_id, version = version + 1 WHERE id = :branch_id AND version = :expected_version`

If the version check fails:

1. The append operation is rejected.
2. The newly created Node is NOT lost (it remains in the repository as an immutable node).
3. The caller is notified of the conflict and can choose to retry, fork a new branch, or inspect the competing node.

## Consequences

### Benefits

- Lock-free branch updates with high read throughput.
- Guarantees branch consistency under concurrent writes.
- Conflicts naturally yield divergent branch candidates rather than silent data loss.

### Costs

- Callers must handle CAS conflict errors and implement retry or branching policies.
- Repository implementations must support atomic conditional updates.

## Alternatives Considered

### Pessimistic Row Locking (SELECT FOR UPDATE)

Lock the branch for the entire duration of an LLM generation.
_Rejected_: LLM inference takes seconds to minutes; holding pessimistic locks that long ruins system throughput.
